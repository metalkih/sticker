# 에이전트 세션과 사용자 확인함

관련 기능: [#1](https://github.com/oozoofrog/sticker/issues/1), [#9](https://github.com/oozoofrog/sticker/issues/9), [#10](https://github.com/oozoofrog/sticker/issues/10), [#11](https://github.com/oozoofrog/sticker/issues/11).

## 기록의 의미

- **에이전트 기록**은 실행별 세션 목록입니다. 같은 에이전트·프로젝트라도 외부 세션 ID가 다르면 별도 기록이며, 한 세션의 연결 이슈는 변경할 수 없습니다.
- 결과·오류만 있고 작업/대기 상태 보고가 없으면 **기록 수신 (작업 상태 보고 없음)**으로 표시하며 작업 중·대기라고 추정하지 않습니다.
- 작업·대기·입력 필요·결과 검토 필요·종료는 **인증된 에이전트의 자기 보고**입니다. 실제 프로세스를 감시하거나 검증하지 않습니다.
- 최근 서버 수신 시각이 **5분을 초과**하면 오래된 자기 보고입니다. 발생 시각을 과거로 보내도 새 보고의 신선도는 서버 수신 시각으로 계산합니다. UI도 별도 시계로 상태를 다시 계산하므로 새로고침 실패가 실행 중 표시를 연장하지 않습니다.
- 상세 타임라인은 **발생 시각 → 서버 수신 시각 → eventId** 오름차순입니다. 역순 도착도 이 기준으로 표시하고 두 시각을 모두 보여줍니다.
- `end`는 에이전트의 종료 보고일 뿐, 소유자 종결이 아닙니다. 세션·요청 종결은 이슈를 종료하지 않습니다.
- 사용자 확인함은 입력과 결과 검토를 나눕니다. 답변은 특정 요청 ID에만 저장됩니다. 답변 기록·검토 종결은 실행, 승인, 재개, 외부 알림이 아닙니다. 이슈 종료가 필요하면 연결 이슈를 열고 기존의 별도 소유자 종료 흐름을 사용하세요.

목록·상세·확인함은 프로젝트 필터, 빈 상태, 로딩, 실패·재시도와 마지막 성공 확인 시각을 표시합니다. 일시적 조회 실패 때 기존 기록과 답변 초안은 유지하며, 권한 상실·삭제 응답 때는 해당 기록을 숨깁니다. 충돌 후에는 최신 요청을 다시 읽고 작성한 초안을 유지합니다. 세션·요청 ID는 URL 해시에 저장되어 직접 링크·새로고침·뒤로가기로 같은 항목을 엽니다.

## HTTP

기존 `/api` 인증·출처 검증이 모든 경로에 적용됩니다. 작성자·에이전트 ID는 요청 본문이 아니라 인증된 Actor에서 결정합니다.

| 경로                                          | 용도                                                           |
| --------------------------------------------- | -------------------------------------------------------------- |
| `GET /api/sessions?projectId=...`             | 범위 내 세션 목록                                              |
| `GET /api/sessions/:id`                       | 세션, 이벤트, 요청과 응답                                      |
| `POST /api/sessions/events`                   | 에이전트 자신의 세션에 이벤트 추가                             |
| `GET /api/inbox?projectId=...&completed=true` | 미처리 또는 처리 완료 요청; 에이전트는 자신의 요청만 목록 조회 |
| `GET /api/requests/:id`                       | 범위 내 정확한 요청 조회                                       |
| `POST /api/requests/:id/responses`            | 소유자 답변 기록                                               |
| `POST /api/requests/:id/close`                | 소유자 요청 종결                                               |
| `POST /api/sessions/:id/close`                | 소유자 세션 종결                                               |

이벤트 예시 (식별자는 각 설치에서 조회한 값으로 대체):

```json
{
  "projectId": "project-id",
  "issueId": "issue-id",
  "externalSessionId": "run-2026-10-28-a",
  "eventId": "question-1",
  "kind": "request",
  "requestKind": "input",
  "message": "다음 변경 범위를 확인해 주세요."
}
```

`occurredAt`은 선택적 ISO UTC 시각입니다. 저장 전에 UTC 밀리초 정밀도로 정규화하므로 초 단위와 소수점 시각이 섞여도 시간순 정렬이 유지됩니다. 생략하면 서버 수신 시각을 사용합니다. 잘못된 시각과 서버보다 1분 넘는 미래 시각은 거부합니다. `report`는 `state: working|idle|blocked`, `request`는 `requestKind: input|review`를 받으며 `result`, `error`, `end`는 메시지만 받습니다. 임의 메타데이터·작성자 지정·명령 실행은 허용하지 않습니다. 본문 및 응답은 브라우저와 서버가 공유하는 엄격한 Zod 계약으로 검증합니다.

동일 `(인증 에이전트, 프로젝트, 외부 세션 ID, eventId)`와 같은 내용의 재전송은 저장된 이벤트를 반환합니다. 내용이 다르면 `409 EVENT_CONFLICT`입니다. `eventId`를 재사용해 새 보고처럼 시간을 갱신하지 않습니다. 기존 보고 API의 명시적 이벤트 재시도도 새 스냅샷을 쓰지 않으므로 더 최근의 상태·메시지·수신 시각을 과거 보고로 덮어쓰지 않습니다.

답변 본문은 `{ revision, operationId, body }`, 종결 본문은 `{ revision, operationId }`입니다. `operationId`는 클라이언트가 만든 UUID입니다. 같은 답변 작업 키는 같은 요청·revision·내용에만 재사용할 수 있습니다. 오래되거나 처리된 요청은 `409 REVISION_CONFLICT`, 작업 키 내용·대상 재사용은 `409 OPERATION_CONFLICT`입니다. 쓰기 불가·프로젝트 범위·종료 이슈 보호는 서버에서 다시 검사합니다.

## 기존 보고 호환성

`agent_reports`와 기존 `/api/reports`, `sticker_report_status`, `sticker_list_reports` 응답 형태는 유지합니다. 예전 호출은 이슈별 `legacy:<issueId>` 세션으로도 기록되므로 다른 이슈의 세션이 덮어써지지 않습니다. 기존 스냅샷 API 자체는 에이전트+프로젝트 최신 한 건이므로 새 목록 화면의 원본이 아닙니다. 예전 `blocked`는 막힘이라는 자기 보고로만 보존하며 사용자 입력 요청을 추정하지 않습니다. 확인함 항목은 명시적인 `request` 이벤트만 만듭니다.

기존 보고 호출에도 `externalSessionId`와 `eventId`를 함께 추가할 수 있습니다. **eventId가 없는 예전 호출의 재시도 중복 제거는 보장하지 않습니다.** 정확한 실행 이력에는 새 이벤트 API/MCP 도구를 사용하세요. 예전 호출에는 실행 식별자가 없으므로 동일 이슈의 호환 세션을 계속 사용합니다. 종료 보고 뒤 새 작업/대기/질문 보고가 오면 호환 세션의 현재 종료 표시는 해제하지만 기존 종료 이벤트는 보존합니다. 이를 새 실행의 검증으로 해석하지 않습니다. 명시적 외부 세션 ID를 사용하는 새 API는 이 호환 처리를 하지 않습니다. v1 데이터는 기존 보고 한 건당 표시된 레거시 세션·이벤트 한 건으로만 옮기며 존재하지 않는 이전 이력·질문을 추정하지 않습니다.

## 저장소와 확장 지점

- `server/migrations/001-initial.ts`는 원래 v1 DDL입니다. `002-sessions.ts`가 세션·이벤트·요청·응답 테이블을 추가합니다. `migrations/index.ts`는 모든 대기 마이그레이션을 한 `BEGIN IMMEDIATE`로 실행하고 실패 시 스키마와 버전을 함께 롤백합니다. 더 최신 DB는 저널 모드 변경 전에 거부하고 초기화 실패 시 연결을 닫습니다.
- `server/schema-manifest.ts`는 실제 지원하는 **v1/v2만** 선언합니다. 백업 검증은 각 버전의 테이블·열, 무결성·외래키 및 첨부 크기·바이트를 읽기 전용으로 확인합니다. v1 백업은 그대로 검증되고, 복원 뒤 앱 시작 때 v2로 올라갑니다. 검증기가 마이그레이션하지 않습니다. 기존 비공개 파일 저장 위치는 바뀌지 않습니다.
- `Store` 공개 API는 유지합니다. `StoreContext`는 단일 DB 연결·트랜잭션·시계·프로젝트 범위·쓰기/소유자 검사·종료 이슈 검사·SQL 도우미·작성자 활동을 공유합니다. SQL 테이블 이름은 고정 허용 목록입니다. 새 기능은 같은 컨텍스트를 받는 서비스와 계약·라우트·MCP 등록 모듈로 확장합니다.
- 다음 기능은 새 순차 마이그레이션, 누적 manifest와 지원 버전 판별, 컨텍스트의 필요한 고정 테이블, facade 서비스 노출, 인증 뒤 라우트 등록을 함께 추가해야 합니다. 미래 기능용 테이블이나 필드 복원 기능은 아직 구현하지 않습니다.

## 검증

`npm test`는 실제 SQLite/HTTP/공식 MCP SDK/React DOM 회귀를 실행합니다. `npm run typecheck`, `npm run lint`, `npm run build`, `npm run test:production`, `npm run format:check`도 실행하세요.

실제 브라우저 시나리오는 `tests/ui/sessions.spec.ts`입니다. `npm run build` 후 `npm run test:ui`로 실행하며, 임시 DB·가상 에이전트만 사용합니다. 데스크톱과 375px 모바일에서 카드 키보드 진입, 직접 링크·새로고침·뒤로가기, 긴 출력, 요청 답변·충돌 초안·처리 완료, 실패한 새로고침·필터를 검사합니다. DOM 테스트만으로 시각·모바일 검증을 통과했다고 간주하지 마세요. 브라우저 실행 제한이 있는 환경에서는 별도 브라우저/CI 결과가 필요합니다.
